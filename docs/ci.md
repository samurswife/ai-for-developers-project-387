# Проверки pull request

`Project checks` запускается на `pull_request` в `main`, push основной ветки и вручную.
Обновление PR отменяет устаревший запуск. Проверки и браузерный job используют только `contents: read`,
без секрета модели и OIDC. Код PR исполняется в обычном `pull_request`, без `pull_request_target`.

## Проверки и версия

- `check` выполняет полный `mise run check` и Docker-проверку.
- `browser-head` работает отдельно на событии PR: явно получает `github.event.pull_request.head.sha`,
  сверяет его с `git rev-parse HEAD`, собирает приложения и выполняет `mise run test:evidence`.

Оба job проверяют head автора. Это не временный merge-коммит GitHub.
Проверка браузера использует настоящие приложения на свободных локальных портах в отдельном runner.
Каждый сценарий получает изолированное хранилище; новое облачное окружение не требуется.

Обязательные проверки в защите `main`: `check` и `browser-head` от GitHub Actions.
Перед мержем человек сверяет успешные статусы, поведение со спецификацией и текущий SHA артефакта.
В интерфейсе они показаны внутри workflow `Project checks`; API использует имена jobs.

## Браузерный артефакт

В конце `browser-head` публикуется `browser-pr-<PR>-<SHA>-<run_id>-<attempt>` со сроком хранения 30 дней.
Загрузка выполняется и после ошибки тестов. Отчёт в Summary запуска содержит ссылку на скачивание.

Артефакт содержит:

- `checkout-sha.txt` — результат `git rev-parse HEAD` до установки инструментов;
- `head-sha.txt`, `result.json` и `summary.md` — фактически проверенный SHA, ожидаемый SHA, номер PR,
  run/attempt, команда, время, статус и список сценариев;
- `test-results.json` — результат Vitest с именами тестов, статусами и сообщениями проверок;
- `browser.log` — вывод запуска;
- `scenarios/<id>/scenario.json`, `trace.zip` и скриншоты страниц для каждого браузерного контекста;
- `job.json` — исходы подготовки и запуска, в том числе если установка не позволила начать тесты.

Trace явно включён при успехе и ошибке, сохраняется до закрытия браузера.
Playwright trace содержит действия, сеть и снимки DOM; утверждения Vitest находятся в `test-results.json`.
`result.json` получает `passed`, только если все тесты прошли и для каждого есть trace и скриншот.
Пропуск теста, пустой результат, ошибка записи, отсутствие свидетельства или несовпадение SHA дают ошибку.
При сбое подготовки сохраняется `infra`, успешная браузерная проверка не заявляется.

Перед мержем:

1. Возьмите текущий head SHA из PR, например `gh pr view N --json headRefOid --jq .headRefOid`.
2. Откройте успешный `browser-head` и скачайте его артефакт по ссылке в Summary или разделе Artifacts.
3. Сверьте SHA в имени, `checkout-sha.txt`, `head-sha.txt` и `result.json` с текущим head PR;
   проверьте `status: passed`, `dirty: false` и успешные исходы в `job.json`.
4. Откройте `summary.md`, результаты конкретных сценариев, скриншоты и trace:
   `mise exec -- pnpm --filter @calendar/smoke-tests exec playwright show-trace /путь/к/trace.zip`.
5. Зафиксируйте решение человека в PR. После нового push повторите проверку: старый артефакт
   относится к прежнему SHA. Отсутствие артефакта не заменяется зелёным статусом другого job.

Авторевью может завершиться раньше CI и не видеть готовый артефакт: окончательная сверка остаётся за человеком.
Для PR, созданного `GITHUB_TOKEN`, GitHub может потребовать **Approve workflows to run**.

## Сценарии спецификации

Инфраструктура записывает все текущие браузерные smoke и будущие тесты, использующие `browserEvidence`.
Для [спецификации #6](https://github.com/samurswife/ai-for-developers-project-387/issues/6)
реализация #7–#9 должна добавить сквозной сценарий Красноярск ↔ Москва и соседний случай Гонолулу
с переходом даты. Сравните реальные имена и результаты тестов с согласованными критериями.
Существующие тесты фиксированного московского времени не доказывают ещё отсутствующее поведение #6.

Новый браузерный контекст подключается через `browserEvidence(context)`:
вызов до первого действия, возвращённая функция — в `finally` до закрытия браузера.
Общий `browserScenario` уже выполняет это автоматически.

## Локальный запуск

`BROWSER_ARTIFACT_DIR=/tmp/calendar-browser-<новое-имя> mise run test:evidence` собирает приложения
и сохраняет тот же формат свидетельств. Можно проверить ожидаемый SHA через `EXPECTED_HEAD_SHA`.
Без переменной каталога используется `.cache/browser-evidence`; перед следующим запуском выберите
новый пустой каталог, чтобы не использовать прежние результаты.

Локально записывается признак `dirty` для незакоммиченных изменений. В CI такой checkout отклоняется;
локальный прогон изменённой рабочей копии не является свидетельством чистого head PR.
