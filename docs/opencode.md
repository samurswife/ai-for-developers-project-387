# OpenCode в GitHub

Локальная работа ведётся в Codex. OpenCode запускается в GitHub Actions тремя путями:

- вручную — по комментариям `/oc <задание>` или `/opencode <задание>` в issue, обсуждении PR
  или комментарии к строке PR. Команда должна быть отдельным словом.
- автоматически — по открытию нового issue отдельным workflow [opencode-triage.yml](../.github/workflows/opencode-triage.yml).
- независимо от реализации — для авторевью PR через [opencode-review.yml](../.github/workflows/opencode-review.yml).

События edited/labeled не запускают агента. Комментарий запускает исправление только с командой человека.
Отдельный [opencode-result.yml](../.github/workflows/opencode-result.yml) публикует итог ручного запроса
на событии `workflow_run: completed`; модель он не вызывает.

## Подготовка и ревью PR

Для реализации согласованной спецификации оставьте команду в исходном issue:
`/oc запусти скилл implement-spec для спецификации #N и её тикетов; сначала прочитай AGENTS.md и docs/agents/`.
Передайте ссылки на спецификацию, тикеты и комментарий согласования человеком.
Скилл собирает результат в общей ветке и проводит итоговое ревью собранных изменений.

Заполните [шаблон PR](../.github/pull_request_template.md): исходное обращение, спецификацию,
тикеты, согласование и `Closes #N` для выполненных задач. Для инфраструктурного изменения укажите
его собственный тикет и согласованный объём. Запишите команды и результаты проверок, проверенный
head SHA и ссылки на прогоны; обоснуйте риск последствиями ошибки и опишите откат с проверкой восстановления.
Неприменимые проверки сопровождайте объяснением.

Передайте независимому ревьюеру [REVIEW.md](../REVIEW.md), источники из PR, базовый и head SHA,
diff и результаты CI. Отдельное ревью PR не продолжает сессию реализации.
Workflow передаёт этот контекст независимому ревьюеру автоматически по правилам раздела ниже.

Человек разбирает замечания и явно поручает необходимые исправления:

- Общий комментарий: `/oc исправь подтверждённые замечания из <ссылка>; продолжай в этой же ветке PR`.
- Комментарий к строке diff: `/oc исправь эту ошибку и добавь защиту от повторения; продолжай в этой же ветке PR`.
  Контекст файла, строки и diff приходит из события `pull_request_review_comment`.

Дождитесь завершения запроса перед следующим. Комментарий ревьюера без команды человека не поручает правку.
Для каждой проблемы сохраните исправление либо объяснение отклонения; для подтверждённого дефекта добавьте
регрессионную проверку или другую подходящую защиту. После push повторите затронутые проверки и обновите
SHA и свидетельства в PR. Перед мержем человек сверяет поведение со спецификацией, текущие результаты CI
и браузерные свидетельства и фиксирует решение. Правила итогового сообщения и release PR — в
[инструкции по релизам](releases.md).

OpenCode не имеет прав на создание и изменение файлов `.github/workflows/`. Такие изменения готовятся
локально в Codex и проходят отдельную проверку доступа человеком; расширять права App для этого не требуется.

## Независимое авторевью PR

Workflow `opencode-review.yml` слушает `pull_request` с типами `opened`, `synchronize`, `reopened`,
`ready_for_review` для `main`. Draft, закрытые PR и ветки fork пропускаются.
Отдельный job до передачи секрета проверяет текущие права `write/admin` автора и инициатора запуска,
включая инициатора Re-run. Для `opencode-agent[bot]` и `github-actions[bot]` есть явный допуск:
у App-автора API прав участника может возвращать `none`, поэтому общего запрета на Bot нет.
Ошибка API прекращает допуск. Перед моделью состояние PR, права и head SHA проверяются повторно.

Ревью запускает обычный `opencode run --format json`, а не `opencode github run`, с закреплённым CLI
и новой сессией. OIDC и App-токен ему не нужны. Права job: `contents`, `issues`, `actions`, `checks`,
`statuses` — `read`; `pull-requests` — `write` для комментария. GitHub-токен процессу модели не передаётся.
Секрет `OPENCODE_API_KEY` доступен только допущенному шагу CLI.

Workflow читает через GitHub API:

- `REVIEW.md`, `AGENTS.md`, словарь и документы предметной области из базового SHA PR;
- diff и полное текстовое содержимое изменённых файлов из точного head SHA;
- связанные Issues и комментарии согласования по ссылкам из PR, критериев и тел связанных Issues;
- предыдущие общие и построчные комментарии PR, итоговые отзывы Review (включая Request changes),
  checks, statuses и запуски Actions проверяемого SHA.

Итоговые отзывы загружаются отдельно через
[`pulls.listReviews`](https://docs.github.com/en/rest/pulls/reviews#list-reviews-for-a-pull-request)
с пагинацией: в `prior_reviews` передаются последние 20 отзывов с текстом, автором, состоянием, временем
и SHA проверенной версии. Это сохраняет замечания из итогового текста, даже если нет общих или построчных
комментариев. Усечение истории/текста и ошибка загрузки явно отражаются в пробелах контекста.

Источники Issues ограничены этим репозиторием и историческим проектом `ai-for-developers-project-386`
того же владельца. Недоступное согласование, пропущенные или усечённые данные записываются в пробелы контекста.
Контекст ограничен первыми 30 изменёнными файлами, 64 тысячами символов на файл и 20 источниками Issues;
объём свыше 750 тысяч символов требует проверки человеком без вызова модели.
Отсутствие артефакта или ещё работающий CI не считается успешной проверкой.

Checkout и установка зависимостей проекта в авторевью отсутствуют. Код и конфигурация PR не исполняются.
CLI работает в отдельном временном каталоге; настройки проекта, внешние скиллы и плагины отключены,
все инструменты агента запрещены. Модель анализирует уже подготовленный контекст и возвращает текст.
Отдельный шаг без модели публикует его через GitHub API с SHA, моделью и ссылкой на логи.
Если PR успел измениться, закрыт или снова переведён в draft, результат не публикуется.

Модель ограничена десятью минутами, job — пятнадцатью; оставшееся время нужно для подготовки и публикации.
Группа concurrency `opencode-review-<repository>-<PR>` с `cancel-in-progress: true` отменяет устаревшее ревью.
Ошибка подготовки или ключа публикуется как `infra`, тайм-аут — `timeout`, другой сбой или пустой ответ —
`agent_failed`. Job при этом завершается ошибкой. Отменённый устаревший запуск не публикует итог;
проверяйте статус нового запуска для текущего head.

Авторевью возвращает замечания, но не исправляет код и не принимает решение о мерже.
Человек разбирает каждый пункт и вызывает `/oc` только для подтверждённых исправлений.
При повторном ревью модель получает предыдущий разбор; автоматической цепочки исправлений нет.

PR, созданный или обновлённый с `GITHUB_TOKEN`, может ожидать **Approve workflows to run**.
Для PR OpenCode App запуск обычно автоматический. При отсутствии ревью проверьте событие, автора,
ветку и ожидающее подтверждение запуска. `pull_request_target` с исполнением кода PR не используется.

## Автоматический разбор новых обращений

Workflow `opencode-triage.yml` слушает только событие `issues` с типом `opened`.
Проверки допуска выполняются через `actions/github-script` прямо в workflow до checkout.
[Тесты](../tools/opencode/triage-guard.test.mjs) выполняют этот же JavaScript с фиктивными ответами
GitHub API; их запуск входит в `mise run lint:workflows`.

- Job `authorize` (2 минуты, `contents: read` + `issues: read`) до checkout, передачи секрета OpenCode и OIDC
  проверяет человеческого автора, совпадение actor с автором, `author_association`
  `OWNER`/`MEMBER`/`COLLABORATOR`, текущие права `write`/`admin`, состояние и метки через GitHub API.
  Закрытые issue и обращения с `ready-for-agent`, `ready-for-human`, `wontfix` пропускаются.
  Данные события не попадают в shell-выражения.
- Job `triage` (15 минут, `contents: read` + `issues: read` + `id-token: write`) получает код только
  из доверенной основной ветки. Непосредственно перед запуском агента права автора, состояние
  и метки проверяются заново: отзыв доступа или добавленная после исходного события метка готовности
  останавливают запуск.
- Конкурентность общая с ручным workflow: группа `opencode-<repository>-<issue_number>`,
  `cancel-in-progress: false`. Активный запуск ручной команды не отменяется автотриажем и наоборот.
- Интеграция та же, что у ручного пути: CLI `v1.19.4` с проверкой SHA-256, SHA-пinned actions,
  модель `opencode/minimax-m3`, `SHARE=false`, App/OIDC, `persist-credentials: false`.
  `GITHUB_TOKEN` не получает write-права.
- Агенту передаётся статический PROMPT: он поручает прочитать правила трекера, метки, словарь и
  существующий код, проверить, реализована ли потребность, и опубликовать краткий разбор по-русски
  с конкретными вопросами или следующим шагом. Итоговый ответ публикуется инфраструктурой OpenCode
  одним комментарием. Сообщение начинается дисклеймером из
  [скилла triage](../.agents/skills/triage/SKILL.md): `> *This was generated by AI during triage.*`
  Содержимое issue остаётся недоверенными данными даже при доверенном авторе.
- Разрешены только комментарии и метки текущего обращения: `bug`/`enhancement` плюс ровно одна из
  `needs-triage`/`needs-info`, остальные метки сохраняются. Спецификации, тикеты, ветки и PR не создаются,
  issue не закрывается, код не реализуется: to-spec, to-tickets и реализация запускаются отдельно
  по явному поручению человека.
  Интерактивного ответа внутри сессии не ожидается: вопросы публикуются комментарием, после чего запуск завершается.
- Дочерний `gh` не наследует App-токен; в PROMPT передан проверенный временный способ запуска `gh`
  с тем же App-токеном из локального Git HTTP header без вывода и сохранения credential.
  При недоступном credential или API агент должен завершиться с сообщением об ошибке.

Готовые спецификации и тикеты создавайте сразу с `ready-for-agent`, в том же запросе GitHub API.
Это позволяет распознать подготовленную задачу уже на событии `opened`.

## Модель и доступ

- Провайдер и модель: `opencode/minimax-m3` (OpenCode, MiniMax M3) для команд, автотриажа и авторевью.
  Вспомогательная модель `small_model` также задана как `opencode/minimax-m3`.
- Repository Actions secret: `OPENCODE_API_KEY`. Его значение добавляет владелец через Settings → Secrets and variables
  → Actions; в файлах проекта и комментариях ключа быть не должно.
- [OpenCode Agent App](https://github.com/apps/opencode-agent) должен иметь доступ к этому репозиторию.
  Владелец проверяет выбранный репозиторий и подтверждает права в Configure установки App.
- Workflow использует OIDC для получения токена App. `GITHUB_TOKEN` имеет только права чтения;
  право App оставлять комментарии, создавать ветки и PR определяется установкой App, а не этим ограничением.
  Это относится к ручному обработчику и автотриажу; отдельное авторевью использует описанные выше права.

При ошибке авторизации сначала проверьте актуальность ключа в секрете `OPENCODE_API_KEY`.
Имя секрета сохраняется при смене модели; ключ не записывается в исходники, комментарии и артефакты.
Проверка каталога локального CLI не подтверждает доступ ключа раннера: его проверяет реальный запуск Actions.

## Ограничения запуска

Ручной workflow после допуска и резервирования попытки получает полную историю доверенной основной ветки,
устанавливает mise `2026.10.25`, инструменты из `mise.lock` через `--locked` и выполняет `mise run setup`
(зависимости, Chromium, Git-хуки). Подготовка выполняется до передачи ключа модели; её ошибка получает `infra`.
Агенту не требуется самостоятельно устанавливать Node.js или искать инструменты в домашнем каталоге.
При переключении CLI на ветку PR используется уже подготовленная среда; изменение набора инструментов
требует отдельной проверки совместимости.

В runtime-конфигурации запрещены интерактивные вопросы, подтверждение повторяющихся вызовов (`doom_loop`),
чтение `.env`/`.env.*` кроме `.env.example` и доступ к внешним каталогам. Для временных worktree и заметок
разрешён только `$RUNNER_TEMP/opencode-work/`; используйте этот каталог для артефактов вне checkout.
Пути внутри репозитория доступны по обычным правилам OpenCode. Это настройки инструментов агента,
а не изоляция процессов ОС; существующий доступ shell и App не расширяется.
Перед моделью закреплённый CLI компилирует правила агентов `build`, `general`, `explore`,
а `tools/opencode/check-permissions.mjs` проверяет фактический отказ внешнему домашнему каталогу,
разрешение временной рабочей области и отсутствие действующих правил `ask`.
В CI та же проверка запускается без ключа модели, вместе с воспроизведением прежнего `ask` на старой конфигурации.
Семантика разрешений описана в [документации OpenCode V1](https://opencode.ai/v1/docs/permissions/).

Отдельная задача до checkout и передачи секрета проверяет явную команду, человеческого автора,
совпадение автора с инициатором и текущие права `write/admin` через GitHub API.
Ошибка проверки останавливает запуск. PR из форков отклоняются.
Агент начинает с основной ветки; при работе с PR CLI переключается на его ветку после проверки.
Содержимое issue и PR остаётся недоверенным контекстом даже при доверенном инициаторе.

Запуски обоих типов комментариев сериализованы по номеру issue/PR; активный запуск не отменяется новым.
Исполняющий job повторно проверяет права автора и инициатора Re-run, состояние и репозиторий PR.
Проверка доступа ограничена двумя минутами, бюджета — тремя, установка mise — пятью,
зависимостей — восемью, CLI — тремя, правил — двумя. Модель ограничена 45 минутами через `timeout`, job — 70.
Автотриаж и авторевью сохраняют собственные тайм-ауты. Публичный sharing сессии отключён.
Workflow не включает автоматическое слияние PR.

## Предел запусков на PR

В одном PR допускаются **три** запроса человека, общих для `issue_comment` и `pull_request_review_comment`.
Команда реализации в исходном issue, автотриаж и независимое авторевью этот бюджет не расходуют.
Смена SHA и новый push бюджет не сбрасывают. Новый PR получает отдельный бюджет.

Шаг `Reserve PR attempt` находится в исполняющем job до checkout, установки CLI и передачи секрета.
Начало этого шага — допуск попытки: она расходуется и при последующей отмене, тайм-ауте, ошибке подготовки
или агента. Проверка выполняется заново при Re-run всего запуска или только исполняющего job.
Повтор только другого job не расходует попытку. Запросы, отклонённые проверкой доступа или отменённые
в очереди до резервирования, не допускаются; GitHub concurrency не гарантирует FIFO и может заменить
ожидающий запуск новым. Дожидайтесь завершения одной команды перед следующей.

Источник счётчика — история этого workflow в Actions. Неизменяемое имя запуска `OpenCode PR #N`
связывает оба события с одним PR. Для каждого `run_attempt` читается
[список jobs попытки](https://docs.github.com/en/rest/actions/workflow-jobs#list-jobs-for-a-workflow-run-attempt)
с пагинацией; учитывается начавшийся `Reserve PR attempt`, включая отменённые и ошибочные выполнения.
Текущая попытка исключается из предыдущих. Четвёртый и последующие запросы получают `limit_exhausted`;
до CLI и секрета они не доходят. Текст и удаление комментариев на счётчик не влияют.

У App должен оставаться `actions: read` и отсутствовать право записи workflows; это проверяется
перед бюджетом. Исполняющий job получает только `contents/actions/pull-requests: read` и OIDC.
Ошибка API, неполная история или неожиданная идентичность запуска блокируют вызов модели с `infra`.
Обход истории ограничен 10 тысячами запусков; превышение требует вмешательства человека.

Ограничение действует при сохранённой истории Actions и проверенной конфигурации: удаление запусков,
истечение retention, переименование шагов/workflow или изменение прав администратором меняют условия учёта.
Запуски до установки этой конфигурации без нового имени в бюджет не включаются. Лимит не ограничивает
все расходы по issue и не заменяет ограничения расходов у провайдера.

`OpenCode Result` работает отдельно после остановки исходного runner, в том числе при отмене всего запуска.
Его пять минут не входят в тайм-аут агента. Он проверяет workflow ID, путь, репозиторий и номер попытки,
читает только метаданные jobs и текущий head PR, ничего не исполняет из исходного запуска и не скачивает
артефакты. Права: `actions: read`, `issues/pull-requests: write` для публикации комментария.
Для комментариев PR задаётся `pull-requests: write`, хотя используется endpoint Issues;
одних `issues: write` с `pull-requests: read` оказалось недостаточно (API вернул 403).
`issues: write` сохраняется для отчётов в исходных Issues.
Нет checkout, секрета модели и OIDC. Отчёт содержит причину, последний SHA **на момент отчёта** и ссылку
на конкретный run/attempt; этот SHA не означает, что агент или тесты проверили текущую версию.

Причины: `limit_exhausted` — бюджет исчерпан; `timeout` — лимит времени; `infra` — подготовка,
история или ключ; `agent_failed` — ошибка агента либо отмена. Отмена может потребовать просмотра логов.
Для ошибок статус — «нужен человек»; автоматического повтора нет. `success` означает завершение команды,
а проверку поведения, результатов CI и решение о мерже выполняет человек.
Повторный запуск только отчёта не вызывает модель. При сбое публикации проверьте Actions и повторите
`OpenCode Result`; комментарий с тем же run/attempt от `github-actions[bot]` не публикуется повторно.

Проверка после установки в `main`: в учебном PR последовательно выполните три короткие команды,
смешав общий и построчный комментарии (либо заменив одну попытку на Re-run), затем четвёртую.
Откройте логи четвёртой попытки: `Budget exhausted` выполнен, checkout/установка/`Run OpenCode` пропущены.
Сохраните ссылку на неё и отчёт `limit_exhausted` с текущим head. Не используйте бюджет продуктового PR
для учебного исчерпания. Локальные тесты воспроизводят этот сценарий на исполняемом коде workflow;
реальная проверка событий требует установленного в основной ветке workflow.

## Закреплённая интеграция

OpenCode [прекратил поддержку GitHub Action](https://github.com/anomalyco/opencode/pull/59032).
Использование прежней интеграции согласовано владельцем 2026-11-15.
Исходная [документация V1](https://opencode.ai/v1/docs/github/) остаётся справкой по командам и App/OIDC.

Старый composite action скачивает последнюю версию CLI даже при закреплении SHA самого action.
Поэтому ручной обработчик и автотриаж напрямую запускают его команду `opencode github run` из CLI `v1.19.4`,
проверяя SHA-256 Linux-архива по digest официального релиза.
Авторевью использует обычный `opencode run` той же закреплённой версии с тем же digest.
Сторонние actions закреплены полными SHA с исходными версиями в комментариях.
Обновление версии требует повторной проверки GitHub-команды, digest и совместимости модели.

## Проверки и исключение

Jactionlint `2.4.0` закреплён в `mise.toml` и `mise.lock`.
`mise run lint:workflows` входит в `mise run lint`, `mise run check` и CI. Он линтит все workflow проекта,
включая `opencode-triage.yml`, `opencode-review.yml` и `opencode-result.yml`, и запускает тесты
проверок допуска и бюджета с фиктивными ответами GitHub API.
Тесты авторевью исполняют JavaScript из workflow: допуск, подготовку контекста и публикацию результата.
`.github/workflows/hexlet-check.yml` не изменяется.

В `.github/jactionlint.yaml` разрешено правило `dangerous-triggers` для
`.github/workflows/opencode.yml`. Причина — необходимый `issue_comment` с секретом и OIDC,
защищённый отдельной проверкой текущих прав до запуска агента. Jactionlint не анализирует эту проверку.
Владелец согласовал исключение 2026-11-15; пересмотр — **2026-12-15**.
По истечении срока линтер снова сообщает находку. Остальные проверки остаются включены.

Отдельное исключение `dangerous-triggers` относится только к `opencode-result.yml` до **2026-12-17**:
для отчёта после отмены требуется `workflow_run` и `issues/pull-requests: write`. Защита — проверка идентичности
запуска, отсутствие кода/артефактов исходного запуска, checkout, секретов и OIDC. Исключение и право
публикации требуют отдельного согласования владельцем в PR до мержа.

Для приёмки создайте тестовый issue и оставьте `/oc explain this issue`.
Проверьте успешный запуск OpenCode в Actions и ответ `opencode-agent[bot]` со ссылкой на запуск.
При ошибке установки App или обмена OIDC не расширяйте права `GITHUB_TOKEN` автоматически:
проверьте доступ App и работоспособность прежнего сервиса OpenCode.
