## О проекте

«Календарь звонков» — упрощённый сервис бронирования времени по мотивам Cal.com.

Владелец календаря создаёт типы встреч и публикует доступное время, а гость выбирает свободный слот и записывается на звонок без регистрации.

В приложении один заранее заданный владелец календаря. Авторизация, личные кабинеты и интеграции с внешними календарями отсутствуют.

## Пользовательский сценарий

1. Владелец календаря создаёт тип встречи, указывая название, описание и длительность.
2. Гость открывает главную страницу и нажимает «Записаться».
3. В каталоге гость выбирает подходящий тип встречи.
4. В календаре на ближайшие 14 дней выбирает дату и свободный слот.
5. Гость вводит имя и электронную почту и подтверждает бронирование.
6. Приложение отображает экран успешной записи с информацией о встрече и возможностью записаться снова.
7. Владелец открывает список предстоящих встреч всех типов и видит созданную запись.

## Основная функциональность

### Для владельца

- Создание типов встреч с названием, описанием и длительностью.
- Просмотр списка предстоящих встреч всех типов.
- Просмотр информации о бронировании: тип встречи, дата, время и данные гостя.

### Для гостя

- Просмотр доступных типов встреч.
- Выбор даты и свободного времени в календаре, включая ручной выбор своего часового пояса.
- Бронирование встречи с указанием имени и электронной почты.
- Просмотр подтверждения бронирования.
- Возможность перейти к новой записи.

## Интерфейс

Приложение включает следующие экраны:

- **Главная страница** — описание сервиса и кнопка «Записаться».
- **Каталог встреч** — карточки типов встреч с названием, описанием и длительностью.
- **Выбор даты и времени** — информация о встрече, календарь, ручной выбор пояса гостя и список доступных слотов.
- **Форма бронирования** — выбранные дата и время, поля для имени и электронной почты, кнопка подтверждения.
- **Подтверждение записи** — информация об успешном бронировании и возможность записаться снова.
- **Раздел владельца** — создание типов встреч, настройка пояса и список предстоящих бронирований.

## Часовые пояса на гостевом пути

- Календарь гостя по умолчанию показывает время в поясе браузера; гость может выбрать пояс вручную.
- Ручной выбор сохраняется на всём пути календарь → форма → подтверждение и при возврате назад; между сеансами выбор не хранится.
- На форме бронирования и подтверждении основным является время гостя со своей подписью пояса; ниже дополнительным показывается время владельца с подписью его пояса.
- Пояс владельца гость получает через `GET /api/calendar-settings` на входе на форму и подтверждение и через `Availability.timeZone` там, где доступность уже получена.
- Все представления времени вычисляются на клиенте из UTC-моментов `startsAt`/`endsAt`; сервер не получает пояс гостя.

## Правила бронирования

| Параметр | Значение |
|---|---|
| Часовой пояс | IANA-зона владельца, по умолчанию `Europe/Moscow` |
| Рабочие дни | Понедельник — пятница |
| Рабочие часы | 09:00–18:00 |
| Окно бронирования | 14 календарных дней в поясе владельца, включая сегодня |
| Шаг начала слотов | 15 минут |
| Длительность встречи | От 1 до 540 минут |

- Окно бронирования автоматически сдвигается с течением времени; его границы определяются фактическими сезонными смещениями IANA-зоны владельца на каждую дату.
- Длительность встречи задаётся владельцем при создании типа встречи и может быть любым целым числом минут от 1 до 540.
- Доступные начала встреч рассчитываются с шагом 15 минут.
- Длительность слота соответствует длительности выбранного типа встречи.
- Встреча должна полностью помещаться в рабочие часы владельца.
- Забронировать можно любой свободный слот, начало которого находится в будущем.
- Полное и частичное пересечение встреч запрещено, в том числе для разных типов встреч.
- Следующая встреча может начинаться в момент окончания предыдущей, если это время соответствует шагу начала слотов.
- Правила проверки пересечений действуют и для одновременных запросов.
- Смена пояса владельца пересчитывает будущее расписание, но не сдвигает уже созданные бронирования — их UTC-моменты сохраняются неизменными.

## OpenCode в GitHub

CI `Project checks` проверяет PR в `main` и push основной ветки. Отдельный `browser-head` запускает
приложение из точного head SHA PR и сохраняет результат, Playwright trace и скриншоты в артефакт Actions.
Порядок сверки версии и свидетельств перед мержем — в [docs/ci.md](docs/ci.md).

Workflow [OpenCode](.github/workflows/opencode.yml) запускает агента OpenCode по команде
в комментарии: он читает [правила проекта](AGENTS.md), настройки из [docs/agents/](docs/agents/)
и использует скиллы из `.agents/skills/`. Подробная инструкция — [docs/opencode.md](docs/opencode.md).

| Параметр | Значение |
|---|---|
| События | `issue_comment` и `pull_request_review_comment`, `types: [created]` |
| Команды | `/oc <задание>` и `/opencode <задание>` словом в комментарии |
| Модель | `opencode/glm-5.3-flash-free` во всех сценариях; вспомогательные запросы используют ту же модель |
| Секрет | `OPENCODE_API_KEY`; значение добавляет владелец в Settings, в репозитории его нет |
| Sharing | `SHARE=false`, публичная ссылка на сессию не создаётся |
| Авторизация | OIDC через [OpenCode Agent App](https://github.com/apps/opencode-agent); `contents/actions/pull-requests: read`, `id-token: write`, `persist-credentials: false` |
| Кто вызывает | Доверенный человек с текущими правами `write`/`admin`, совпадающий с автором комментария; боты и PR из форков отклоняются |
| Окружение | До модели: mise и инструменты по lockfile, зависимости и Chromium; проверка правил без интерактивного ожидания |
| Ограничения | 3 допущенных запроса на PR, общих для обоих видов комментариев; Re-run, отмена и тайм-аут расходуют попытку. Модель — до 45 минут, job — 70; сериализация по номеру issue/PR |

Команда проверяется дважды: CLI распознаёт mentions `default` (`/oc`, `/opencode`),
а job авторизации фильтрует комментарии по этим же словам до checkout и передачи секрета.
Исполняющий job повторяет проверку доступа и проверяет бюджет по истории Actions до каждого вызова модели.
Отдельный [OpenCode Result](.github/workflows/opencode-result.yml) публикует причину, последний SHA и ссылку
на логи без модели, в том числе после отмены запроса. У него `actions: read`, `issues/pull-requests: write`;
секреты, OIDC и checkout отсутствуют. Подробности — [предел запусков](docs/opencode.md#предел-запусков-на-pr).

Новые issue разбираются автоматически отдельным workflow
[opencode-triage.yml](.github/workflows/opencode-triage.yml) на событии `issues: [opened]`.
До checkout проверяются доверенный автор, его текущие права и актуальные
метки issue: закрытые и обращения с `ready-for-agent`, `ready-for-human` или `wontfix` пропускаются.
Автотриаж ограничен комментарием и метками текущего обращения (`bug`/`enhancement` плюс
`needs-triage` или `needs-info`); спецификации, тикеты и реализация запускаются отдельно
по явному поручению человека. Перед запуском агента права и готовность issue проверяются повторно.
Подробное описание — [docs/opencode.md](docs/opencode.md#автоматический-разбор-новых-обращений).

OpenCode прекратил поддержку GitHub Action, а прежний composite action скачивал CLI версии `latest`
даже при закреплении SHA самого action. Поэтому workflow запускает закреплённый CLI `v1.19.4` напрямую
и сверяет SHA-256 архива с digest официального релиза. Локальная работа остаётся в Codex;
OpenCode используется только в GitHub.

### Подготовка и ревью pull request

Описание PR заполняется по [шаблону](.github/pull_request_template.md): источники и согласование,
проверки с SHA и ссылками на прогоны, риск и способ отката.
[Критерии ревью](REVIEW.md) определяют проверку календаря и формат подтверждённых замечаний.
Workflow [OpenCode Review](.github/workflows/opencode-review.yml) независимо проверяет открытые PR в `main`
при открытии, обновлении, повторном открытии и снятии draft. Он допускает доверенных авторов и явно разрешённые
App-боты с ветками этого репозитория. Ревью получает снимки файлов и контекст Issues, не исполняет код PR
и публикует комментарий с проверенным SHA. Тайм-аут модели — 10 минут, задания — 15; устаревший запуск отменяется.
Замечания разбирает человек, который отдельно поручает исправления командой `/oc`.
Порядок подготовки PR и работы с комментариями описан в [docs/opencode.md](docs/opencode.md#подготовка-и-ревью-pr).

## API

API разрабатывается на основе TypeSpec-контракта.

Из TypeSpec генерируется OpenAPI-спецификация, на основе которой создаётся типизированный клиентский SDK для frontend-приложения.

Серверные типы и маршруты генерируются, если выбранный фреймворк и инструменты это поддерживают. В противном случае backend реализуется по контракту и проверяется тестами.

## Хранение данных

Данные хранятся в оперативной памяти backend-процесса (in-memory).

При перезапуске сервера созданные типы встреч и бронирования сбрасываются. Постоянное хранение данных не предусмотрено.

На Render Free данные также теряются при остановке сервиса из-за простоя и при новом деплое.
Free-сервис засыпает после 15 минут без входящих запросов; первый запрос после простоя может ждать около минуты.
После пробуждения владелец создаёт типы встреч заново. Приложение рассчитано на один backend-процесс.

## Docker

Нужен запущенный Docker Engine, например Docker Desktop. Выполните из корня репозитория:

```sh
docker build -t calendar-calls .
docker run --rm -e PORT=8080 -p 127.0.0.1:8080:8080 calendar-calls
```

Откройте `http://127.0.0.1:8080`. Контейнер автоматически запускает Node.js от пользователя `node`.
NestJS отдаёт frontend и API на одном порту, слушая `0.0.0.0` внутри контейнера.
`PORT` по умолчанию равен `3000`; при изменении переменной измените и внутренний порт в `-p`.
Генерация контракта и сборка выполняются внутри Docker; локальные зависимости и сгенерированные файлы не нужны.
Проверка готовности — `GET /api/health`.

Полная проверка образа: `mise run test:docker`. Она проверяет порты `8080` и `10000`, бронирование через браузер,
отказ пересекающейся записи и сброс данных после перезапуска. Тестовые контейнеры автоматически останавливаются.

## Render и MCP

Работающее приложение: [Запись на звонок](https://calendar-calls-samurswife.onrender.com).

Приложение разворачивается как один Web Service на тарифе Free, runtime Docker, с контекстом сборки `.`
и корневым `Dockerfile`. Используются `NODE_ENV=production`, `HOST=0.0.0.0` и предоставленный Render `PORT`.
Команду запуска переопределять не нужно. В Settings → Health Checks задайте Health Check Path `/api/health`.

Для подключения Codex к [Render MCP](https://render.com/docs/mcp-server):

1. Войти в Render и подключить GitHub-репозиторий.
2. В Codex открыть Plugins, найти Render и установить интеграцию.
3. При первом обращении к Render пройти OAuth-вход в браузере.
4. Запросить список workspace и указать, в каком выполнять деплой.

Ручной вариант без плагина: скопировать `.codex/config.toml.example` в `.codex/config.toml`,
открыть доверенный проект в Codex и выполнить `codex mcp login render`.
Используйте один из способов подключения, чтобы не дублировать сервер.
Шаблон содержит только публичные настройки; токены OAuth хранятся клиентом вне репозитория.
Реальный локальный конфигурационный файл исключён из Git и Docker-контекста.
Для этого приложения не нужны API-ключи или секретные переменные окружения.

Агент создаёт Docker Web Service из основной ветки GitHub-репозитория, ожидает успешный деплой
и проверяет публичный адрес. Render автоматически повторяет деплой при изменении подключённой ветки.

Для повторной браузерной проверки опубликованного сервиса:

```sh
DEPLOYMENT_URL=https://calendar-calls-samurswife.onrender.com \
  mise exec -- pnpm --filter @calendar/smoke-tests exec vitest run production.smoke.test.ts
```

Проверка создаёт тип встречи и бронирование с вымышленными данными. Перед ней дождитесь ответа `/api/health`
после возможного сна сервиса. Весь список тестов запускайте локально без `DEPLOYMENT_URL`.
